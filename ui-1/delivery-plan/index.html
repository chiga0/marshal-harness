    UI-1 技术与并行交付计划¶

    工程决策¶

    React + TypeScript + Vite，Tailwind 与 shadcn 组件，TanStack Query 管服务端缓存；React 本地状态先行，仅在草稿/布局跨页复杂时用 Zustand。版本在开发启动时统一锁定并提交 lockfile，不盲沿用旧 web 依赖范围。浏览器路由采用 React Router 的 hash 路由，避免静态回退歧义。当前无 SSR/SEO 需求，不引入 Next.js。

    目录建议：web/src/app（路由/装配）、components/ui（原子组件）、features/tasks（业务视图）、features/workers、features/artifacts、lib/transport（浏览器请求/校验/摘要）、lib/queries（缓存/刷新）。先保持单 web 包，不建立多端 monorepo 平台。

    现 web 是旧 /api/tasks、/api/runs、/api/stream 控制台。实现前核对旧 Go 的嵌入引用与构建步骤；新 UI 不悄悄重解释旧 API。如 web 同时被旧发行消费，保留独立 legacy 资产入口或把新 UI 移到 apps/task-web，选择记录在集成 PR，不破坏旧 profile。

    浏览器接入按 ADR0098：可选同进程静态托管、精确 Origin 与原 Bearer；默认 API-only 不变。复用 OpenAPI 校验事实并抽取浏览器可用纯模块/Web Crypto 摘要，不能把 node:crypto/http-boundary 打包进浏览器，也不能维护另一套可漂移 DTO。CLI/Node 客户端原兼容测试保留。

    GET 查询按视图激活轮询：活动详情目标 2秒、列表 5秒、隐藏页 30秒或停止；同 key 至多一个在途请求，卸载 abort。失败指数退避上限30秒，401停轮询；mutation零自动重试。以 Task revision 拒绝乱序旧快照覆盖新状态；events 使用现有 cursor 分页并去重，不假设 SSE；终态仍允许手动刷新。列表筛选仅已加载项，UI 标注范围。

    三个粗粒度工作包¶

    先冻结设计 SHA、组件 props、transport 接口和符合 OpenAPI 的样例，再从同一个实现基线派发。每包连续完成可集成成果、自检和交付说明；不是每组件/页面一个任务或 PR。

    工作包 写入范围 完整交付 依赖
    W1 界面基础与任务集合 app、ui、主题、列表/创建视图 可导航的浅深界面、列表与输入全状态 冻结 transport/组件约定；初期用合同样例
    W2 任务详情与业务交互 tasks/detail、workers、artifacts、活动视图 确认、问答、授权、控制、成果和审计全状态 同一组件与 hook 契约
    W3 浏览器接入与打包 transport/queries、API 边界、服务启动/发行 实际 HTTP、浏览器保护、资产装配、安装入口与兼容 ADR0098 接受；单一协议 owner

    主负责人拥有依赖清单/lockfile、共享接口冻结、跨包装配与冲突解决；作者向其提交依赖请求，不并发改共享文件。W1 的 app 根装配交接给主负责人前必须确认停止写入。W2 不自行改 W1 组件，实现需求通过接口反馈聚合解决。

    每个作者独立锁 base/worktree；共享主目录不写。有可消费接口即本地集成，不等全部结束才发现形状不符；中间集成不要求新 PR 或重开模型任务。范围冲突时减少作者，不以占满并发为目标。

    设计审计与开发后审查¶

    设计阶段两位独立审查者分别检查产品/验收和合同/安全；主笔聚合意见修订，一次回审关闭阻塞项。设计问题或未解决假设必须公开，不能声称多方同意就证明实现通过。

    开发完后两个只读 reviewer 并行：产品/前端实现完整性与安全/API/发行兼容；独立验收者对集成候选执行真实验证，作者的自检仅作线索。主负责人若写过集成代码，不为该写入部分自签独立结论，由另一位审查者覆盖。验收记录绑定精确 source SHA、资产摘要、环境和结果；修改后仅重验受影响范围及必要整链，旧证据不覆盖新字节。

    PR 与效率¶

    仓库已发布 v1，按 AGENTS 恢复 PR 流程。建议一个设计 PR、一个完整 UI-1 实现 PR；三作者可有本地多个 commit，不要求各开 PR。不要把所有作者提交 squash 后再首次集成。合并必须 required CI 绿、独立 review 无阻塞、验收完整；产品 Worker 不获 merge 权限。

    默认每作者一次连续实现，聚合反馈后一次集中返修；这不是失败后强制通过或禁止必要修正。超过一次返修仍存在系统性阻塞时，主负责人定位接口/能力原因，避免重复盲派整队。记录总 wall time、人工等待、返工次数、失败尝试和可用 token 来源，不从模型数推断提速。

    两种执行方式¶

    优先选择已有 Agent 直接独立 worktree 并行，设计包就是统一输入；主负责人集中分发、集成与最终验收。该方式不把前端交付绑定到尚未证明的通用编排能力。

    Marshal Task 方式可以作为已支持业务适配内的执行手段，不能把存在 Pi/Qwen Adapter 等同于已支持任意前端仓库交付。启动前只做一次有界预检：固定仓库/base、Git 业务插件范围、多 Worker 配置、实际原生可执行路径/登录、工作包完整传入、依赖安装/浏览器可用、独立验收命令/制品、预算期限/取消与交付路径。若必须先开发新的调度/业务插件才能承担本项目，直接采用独立 Agent 并行；不要把前端项目变成 Marshal 自身能力改造。

    核对发现当前 task-git-business 对整个锁定 base 限制最多64个 tracked 文件，且不支持新增/删除/重命名；本仓基线有1799个 tracked 文件。task-git-live 还是固定双仓文件任务夹具。因此本次不能直接只换 prompt 驱动现有 Marshal Task 完成全仓 UI，采用直接 Agent 并行最省时；通用 Git 能力扩展另行排期。证据见 packages/task-git-business/git.mjs:87 与该包 README、packages/task-git-live/business.fixture.mjs。

    本轮未调用 Pi/Qwen、未创建产品 Task、未执行 E2E。采用哪种方式不改变需求、单写者、独立验收或发布条件。

    发行与交接¶

    一个已验证候选构建一次，UI 静态资产纳入既有 manifest/签名/同包消费；安装包关闭 UI 模式仍支持旧 API 使用。文档提供启用、连接、关闭、升级和回滚到上一包的步骤，不改旧数据库。缓存：带内容 hash 的静态资产长期缓存，HTML 不缓存；升级后不得混用旧 HTML 与新包资源，回滚后重新建立连接。

    发行负责人有维护者权限，独立于产品 Worker。发布范围为 UI-1 随 Marshal 软件包发行，沿既有受保护流程；不能把开发预览地址当正式发布。外部生产目标若后来新增，明确目标与授权后再实施。

    尚需落实的输入¶

    开发前：ADR 接受、设计审查关闭、共享接口/样例与写入 scope、锁定依赖和基线、实际执行者/Provider配置、验收工具与浏览器版本。发行前：真实截图、真实 E2E/兼容结果、资产摘要、独立 verdict、CI 与回滚说明。这些是交付物，不是额外管理平台或微 PR。
