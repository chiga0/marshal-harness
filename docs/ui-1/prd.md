# UI-1 产品需求

## 目标与用户

面向已在本机配置 Marshal 与至少一个原生 Agent 的可信单用户。用户提交业务需求，理解执行方案，处理必要问题，观察团队进展，取得经独立检查的成果。最重要的问题是：正在做什么、在等谁、我需要做什么、成果是否可信且已交付。

成功流程：连接服务 → 新建任务与上下文 → 必要澄清 → 查看真实计划并确认 → 团队执行 → 必要回答/授权 → 独立验收 → 查看成果/下载与所要求的发布后验。零问题任务不制造问卷；未启用发布的任务正常只交付成果。

## 信息架构

产品以「任务工作台 → 当前阶段与需要处理的事项 → 执行成员 → 成果与证据」逐层展开。一级入口保持任务和设置，不增加工作区、角色或连接器管理平台。

任务工作台先显示已加载范围的待处理、推进中、完成、失败或需干预数量，再呈现需求标题、状态、更新时间。任务标识可展开核对，不占主列；计数和筛选不冒称全局范围。

任务详情首屏有稳定标题、阶段带、当前进展和任务历时。阶段带只标注当前可确认的需求、计划、执行、评审、验收、交付位置，前序位置不自动画成成功；失败或取消不高亮交付。Leader 与 Task 版本不一致时，以 Task 当前阶段显示，不用旧 Leader 投影覆盖。没有百分比或预计完成时间。

概览采用主区加团队侧栏：主区按需处理业务问题、计划批准、发布授权，展示团队最近决定；右栏展示执行成员与评审/独立验收/发布/后验。复杂依赖图、需求原文、历史问答与技术审计按需展开。详情保留团队、成果、活动子视图及现有可定位 URL。窄屏自然转为单列。

执行成员按工作目标、角色、Provider 和尝试标识，不让用户靠 hash 区分工作。可读目标只从当前匹配计划取得；不是实际提示词。成员详情呈现公开活动、Provider 报告模型与用量、实际输入观察、历史进展、结果和技术引用。

详细活动来自可选 `Worker.observation`，区分启动、等待响应、明确思考信号、文本输出、工具调用、重试、上下文整理、停止、终态及未知。生命周期和活动分别表达：终态覆盖旧活动；超过15秒无更新标记陈旧，不能推断模型仍在思考。历史有条数和字节上界；截断明确标记，不假称完整日志。公开文本不是隐藏推理，工具种类与状态不是完整工具参数。

实际输入复用 `Audit.prompts`。按 Worker 与 Task 精确关联，区分已准备、已交接、未留存；节选和完整快照分别标明。只有明确留存策略允许的脱敏正文可见，展开完整快照须验证归属、大小和摘要。默认无正文时解释缺失，不能用目标替代。Token 只显示 Provider 明确报告的累计读数和完整性，不累加重复快照，不从上下文窗口占用推算用量。

团队策略从当前 `Leader.lastDecision.evidenceId` 读取原证据，验证制品归属、大小、摘要及决定 callId/摘要后显示 summary 与行动类型。决定不等于行动已执行；无法校验时显示不可用，保留原审计入口。

独立评审直接展示绑定当前决定摘要的原 summary/findings，并校验所属任务、制品状态、长度、摘要及封套，不由另一个模型改写理由。失败任务在当前焦点给出已知原因和执行记录入口；采集等诊断只展示固定类别及来源，历史错误不冒充最终根因。

显式新 Qwen 配置的 `lastResponseUsage` 单独标为最近一次响应，不能与累计用量相加；上下文占用不当作计费 Token，默认零值有缺失说明。未提供费用时不推算金额。

按 ADR0104 启用的一次格式纠错实际发生后，展示已用次数、原失败与后继执行入口，保留原错误。后继状态依赖真实 Worker，不能由预算已消费推断正在运行或已成功；未启用或未发生时不制造用户待办。

新建任务默认使用需求文本、补充背景与附件。高级 JSON 保留 `text/inputRefs` 原能力，两种输入分别保留草稿，仅提交当前选中方式；不用 JSON 作为普通用户前置。创建成功后突出进入任务，技术回执折叠。

## 可验证的体验出口

- 简单任务：在任务概览一次屏幕阅读内识别当前阶段、是否等待用户、如何取得成果。
- 中等任务：两位作者并行和一次返工可追到各自目标、Provider、尝试、活动与实际输入；无法提供的项明确缺失。
- 复杂任务：业务回答、授权、失败、恢复与后验各保留独立状态，不以历史成功掩盖当前阻塞。
- 从任务到成员活动和输入最多两次导航；查看具体 ID 不成为理解业务的前置。
- 200%缩放和375px下保留主操作，正文不造成整页横向滚动；更新不抢焦点和滚动位置。
- 自动化、真实 Agent、浏览器视觉与真人可用性分别记录；实现和 Agent 模拟不自动关闭真人验收。

## 关键交互约定

- UI 展示状态名称来自当前 Node OpenAPI，不沿用旧 Go ACCEPTED/Run 枚举；中文是标签，不能改变机器状态。
- Task 行动取自 allowedActions（approve/answer/cancel/pause/resume/repair）；Worker取消是独立能力，CAS使用所属Task revision；不可用解释原因。Leader 授权遵循 pendingRequest 合同，不能仅由 Task 字符串推导。
- 确认视图冻结用户所见 revision/digest；409 后保留草稿并要求查看新内容，不能自动替换版本再提交。
- mutation 不乐观宣称成功。202 仅按原回执语义显示已受理；随后查询相应资源。重复点击复用同一逻辑请求，丢响应不换 key 或自动重试。
- 刷新后恢复服务查询；token 不持久保存。未决请求只在内存保留，因此每次重新连接均提示「如上次操作中断，请先核对任务与回执」，不能声称识别到具体未决请求或恢复原key/body。页面存活时才可显式原键重放；刷新/崩溃后人工核对，禁止自动创建替代任务。离开前警告仅尽力提供。
- 上传上限按当前合同为单 input 解码后 256 KiB、最多32个 inputRefs；正文与 context 上限按 OpenAPI。附件是业务输入，不是宿主任意路径入口。未引用附件不宣称绑定成功。
- 当前发布仅支持合同声明的本机 JSON create-if-absent，不承诺云端部署。
- 无自由形式通用聊天、手动拖动状态、通用失败重试或任意修复入口；局部 repair 仅在支持合同和条件明确时展示，首版可将其列为只读结果，不增加通用重派按钮。
- Leader pendingRequest.kind=business 使用 leader.reply 的 answer 分支，绑定 requestId/requestDigest/Task revision；选项提交原value而非label；它不走 task.answer，202无Operation，也不显示 Worker deliveryStatus/ACK。其202仅证明该Leader请求被接纳，后续查 Leader/Task投影。预批准与Worker运行问题继续各自的 task.answer 合同。
- 运行记录/制品不足时给出缺失说明；未知用量显示「暂无数据」。不把最后观察时间当模型持续工作证明。

## 非目标

Workspace/Project 注册、多租户/RBAC、Agent/Skill 管理平台、调度工作流编辑器、桌面客户端、移动 App、全局搜索服务、看板拖动、SSE/WebSocket 新协议、任意终端/文件系统访问、公网托管、任意任务零配置以及 UI 自行批准/发布。

## 范围变更

同一需求的可逆排版实现由 Worker 自主决定。新增实体、授权、持久事实、API 操作、发行支持面或减去必需需求，需要主负责人更新设计并重新审查相关范围。不得以「设计未画出」为由省略错误、等待、拒绝或未知状态。
