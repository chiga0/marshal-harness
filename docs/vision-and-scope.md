# 愿景与范围

本文定义产品最终目标、用户价值与长期边界，不记录发布完成状态。安装版本、平台与实际业务支持见 [Roadmap 当前表](roadmap-status.md#业务交付当前表)和[接口支持矩阵](api-support.md)。目标、机器合同和运行证据的关系见[合同适用性](design-contract-map.md)。

## 产品是什么

Marshal 是可自托管、面向可信单用户的 Task-first Agent Team 服务。用户提交需求与上下文，由 Leader 组织有限的专业执行、独立审查和验收，交付可使用的成果；对需要外部操作的任务，交付还包括精确授权、实际操作回执及独立后验。系统持续接收任务，单次执行保持有界，权威事实不依赖某个 Agent 会话一直在线。

**让 Leader 对业务目标负责，让 Agent 发挥专业能力，让 Core 保证执行边界与事实可靠，让最终交付接受独立且贴近真实需求的检查。** 编排次数、Agent 数量和审计记录数量不是产品产出。确定性控制不能保证自然语言理解或业务判断必然正确。

用户主要理解 Task、Worker、Artifact。Plan、Interaction、Operation 和 Attempt 是任务中的必要记录，不要求用户先创建 Workspace、Project、角色、资源或技能目录。仓库、表结构、平台说明和输入文件是 Task 上下文；服务 data-dir 是部署配置，不是业务对象。

## 为谁解决什么问题

| 用户与场景 | Marshal 提供的价值 | 用户仍须提供或判断 |
| --- | --- | --- |
| 个人或可信团队的操作者，提交代码、文档、SQL 等成果任务 | 将需求变为可审查的团队交付，保留输入、反馈、结果和中断处置 | 业务目标、必要的数据访问、模型登录及重要口径 |
| 需要可替换 Agent 和自有数据存储的开发者 | 中立 API 与受信扩展接口，客户入口不绑定某个 Agent 品牌 | 安装并验证适合其场景的执行、业务与检查能力 |
| 维护业务自动化的工程师 | 将外部操作纳入授权、回执、未知结果对账和后验 | 目标系统的真实权限、可查询标识及补偿策略 |
| 审查交付结果的使用者 | 看到成果、独立依据、未完成项、失败原因及发生过的效果 | 主观质量、无法程序判定的业务取舍 |

“可信团队”表示多名人可以围绕同一操作者的服务协作，不承诺多用户身份隔离或多租户授权。普通用户无需理解内部持久格式；部署与扩展开发者才需要阅读机器合同。

## 擅长与适用条件

Marshal 适合目标能够界定、输入可取得、成果可检查、执行和权限可以限定的任务。多个专业工作包存在真正互补性时，可并行形成候选，再针对组合结果验收；简单任务不因团队形式而被迫拆成大量小节点。

软件工程、结构化文件与数据分析产物是典型任务族；领域扩展决定实际可调用的工具和业务断言。默认通用文件模式适合小型 UTF-8 成果：程序验证文件完整性，独立模型 Review 检查语义符合性。它不能仅凭文件合法就证明生产 SQL、补数或线上部署成功。业务族之间的可用范围必须独立声明。

高价值情形包括：多步骤工作容易漏要求、作者总结不能作为验收、执行中断后容易重复操作、需要保存真实交付和决策依据。跨任务连续工作通过新任务引用原需求、成果和事实完成，不依靠无限会话，也不能借新任务隐去原成本或未知效果。

## 不擅长与产品边界

- 不替代强编码 Agent 的单人编辑体验，不保证多 Agent 必然更快或更省钱。
- 不保证任意领域零配置、任意自然语言任务正确、模型永不误解需求。无法取得的输入或不可验证的结果必须明确说明。
- 不将普通宿主子进程、独立目录、环境过滤或工具提示称为恶意代码沙箱；角色职责分离不等于凭据不可达。
- 不以 Skill 安装、原生登录、角色名或模型同意授予外部写权限。真实平台操作需要相应业务能力与授权。
- 不承诺跨系统事务或无条件 exactly-once；未知外部结果先查证，不能盲目重发。
- 不将组织 IAM、多租户、HA、通用拖拽工作流、动态角色平台、技能市场或资源注册设为产品成立条件。

这些边界不是“所有未来扩展禁止”。扩展只有在真实需求成立、相应合同明确且证据支持时才能获得新保证；不因为目标图上画出容器或远程执行就宣布支持。

## 最终目标与成功标准

最终形态是三面职责明确的常驻服务：控制面持有任务语义与授权，执行面驱动可替换的 Agent 和环境，存储面保存可恢复事实与成果。客户端通过统一 HTTP API 创建、确认、观察、干预和消费任务；扩展通过受信接口接入，不重新实现一套业务状态机。

| 目标 | 成立标准 |
| --- | --- |
| 可用业务交付 | 原始需求、确认的交付约定、最终成果与独立证据可对应；遗漏必需要求不能整体成功 |
| 有界自治 | 批准内实现细节由团队推进；目标、必要验收、预算和外部权限的实质变更需要精确确认 |
| 可恢复事实 | 故障后能说明执行归属和真实效果，合法恢复或明确介入，不重复启动和盲重发 |
| Provider 中立 | 替换 Agent、执行环境或存储实现不改变业务语义、证据要求和发布授权；不符合所需能力则拒绝 |
| 可理解的公开接口 | 从需求到交付的正常和失败路径可由标准客户端完成，不靠读私有数据库或人工补状态 |
| 高效且诚实 | 同时记录业务完成率、首次验收、人工介入、交付耗时和可取得用量；缺失计量不填零 |

验收不是单一通过率。要区分正常真实任务、已知缺陷修复、确定性故障反例，以及执行、验收和用户最终体验。评审、平台验证与发布资产各有其范围，不能互相代替。

## 设计取舍

自托管使权威状态、制品与审计可由用户保存，但模型与工具调用的数据是否出域取决于部署和 Provider。保持中立降低品牌耦合，同时要求认真描述不同 Agent 的交互、停止、权限和用量能力，而不是统一成虚假的最低共同保证。

唯一 Application/SQLite 与受信组合减少分布式一致性和运维负担；代价是不能据此宣称 HA 或敌对租户隔离。程序门禁提供稳定的事实与权限约束，独立语义检查和必要的人类判断补足业务含义；代价是验收设计本身仍须评估，不能只让同一种模型重复投票。
