# ADR 0094：可信单用户角色团队与有界授权交付

- 状态：Accepted（2026-09-09；依据用户本轮明确要求可信单用户角色团队，以及随后对全程受管 Leader、Supervisor/Core/Execution 四责边界的明确确认，强 OS 账号/凭据隔离证明后置。此为设计接受，不是实现审查通过或运行许可回执）。
- 适用：ADR0088 的 Node Task 服务，目标支持 profile 名称为 `trusted-single-user`；本稿不新增已可用配置项、API、持久格式或自动发布能力。
- 基线：`31afe269f25241c4ff9fde19c03478cbfddb85a7`。实际成熟度见 [Roadmap](../roadmap-status.md#业务交付当前表)，实施出口见 [Milestone](../agent-team-service-milestones.md)。

## 1. 决策与精确取代范围

当前先交付能完成真实业务的受信角色团队，不以证明同 UID 下完全隔离宿主凭据作为前置。信任单个操作者、其选定的 Agent/模型、受信组合代码与允许执行的业务材料；不支持恶意 Worker、敌对依赖、多租户或凭据窃取对抗。共享 OS 用户意味着这些进程可能触达该用户的文件、原生登录与外部工具，角色名、环境过滤、工具回调和本地 token 均不能证明强隔离。

| 原约束 | 本 profile 的调整 | 不变部分 |
| --- | --- | --- |
| ADR0085 §3、ADR0088 §3：作者可达 Publisher 凭据/已登录发布入口即不进入支持范围，`publication:none` 也不例外 | 对 `trusted-single-user`，不再要求先证明 OS 账号/凭据不可达；明确保留 ambient credential 风险，强隔离作为后继加固支持项 | 作者没有产品发布授权，不主动发现/输出秘密；默认 `publication:none`，原生登录不代表批准任何外部写 |
| Worker/Publisher 分权 | 当前要求产品职责、命令准入与证据权威分离；不宣称已用 OS 身份强制隔离 | 开发者不能自签验收或自行接纳发布，Core 仍独占权威事实；旧 Go/hardened profile 的强边界不变 |
| 首版只下载成果，外部发布全部后置 | 保留下载默认；增加一个明确授权、目标有限、可观察回执的代表性业务发布及发布后验证闭环作为后继完整实现 | 未实施/未实测能力不能从提示词直接启用；无授权、超范围、高风险缺批准或效果未知时拒绝继续写 |
| ADR0085 §6、ADR0088 §2：内置确定性 Supervisor 汇集预算/容量/派发/超时/结果/取消推进职责 | 新 Leader 目标 profile 中：Supervisor 只观察/聚合/通知，业务判断交 Leader，授权/预算/已批准 DAG 调度和硬规则交 Core，所属 start/stop/collect 交 Execution | 一个 Application/Store；旧确定性规则不被 LLM 替代，不加四个服务/第二 scheduler；现 TaskSupervisor 混合实现尚待渐进委托拆分 |
| ADR0091 §1/§3：原计划局部修正只由用户显式 `task.repair` 请求，Planner 仅原计划 | 新机制允许 Leader 在原批准自治范围内请求局部调整，绑定独立意见/失败和当前成果，超目标/成本/高风险须确认 | 原 HTTP 显式 repair、原负 Decision/回执和旧记录不变；新增内部来源及兼容随整链实现冻结，不能伪造旧内容拒收或冒用用户授权 |
| 一次性 Planner 足以代表 Leader | 明确不成立；Leader 由需求/回答、批次结果/求助、集中 Review、交付/后验唤起，读 durable 上下文，输出有限行动 | 进程无需常驻；不新增角色 CRUD、任意动态工作流或第二状态机，现有角色枚举本次不改 |

本 ADR 只改变所列 Node 目标支持面的信任假设和排期。ADR0051/0052/0068、旧 Go 执行/Publisher、hardened conformance、远程认证与全部旧运行记录保持原合同。不得给旧证据改 `production=true`、重签或从本稿推导旧部署已获强隔离证明；后继受支持声明须明确本 profile 和剩余风险，而非隐去限制。

**兼容性**：本次是目标/profile 合同与排期调整，不修改现有 HTTP 请求/响应、角色枚举或持久格式，无数据迁移，不撤回 API-STABLE 已验证范围。它不是当前软件的协议 breaking change，但也不承诺未来发布实现“一切向后兼容”：若新增角色枚举、终态或副作用记录会影响严格客户端/旧 reader，须随完整实现明确 API 版本或兼容方式、格式选择及旧根拒绝/升级策略，不把未识别值静默解释成旧成功。

## 2. 全程受管 Leader 与四责边界

| 职责 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| Leader | 理解目标、提出必要问题和有限分工、协调开发/Reviewer/验收、汇总证据；在既定授权内请求发布并组织发布后验证 | 直接改状态/预算/授权，凭自己的总结签通过，绕过必需 Reviewer 或把发布请求当成功 |
| 开发 Worker | 在批准输入与节点范围内产出候选、报告实际问题，必要时请求业务答案 | 自改验收标准、给自己的成果签权威 Decision、借原生登录自行发布 |
| Reviewer | 独立读取精确候选与证据，提出有界语义意见/集中修正建议 | 为自己参与编写的同一成果承担唯一独立评审，凭角色标签替代真实检查 |
| 验收执行 | 在作者之外验证冻结的整体业务断言与制品；发布后按授权检查实际目标 | 接受作者的 pass 文本、改低原断言、把本地文件存在当外部业务效果 |
| 发布执行职责 | 仅消费已授权且经当前证据接纳的精确成果，执行有限外部动作并返回真实回执 | 自授发布权限、改变目标/成果、在 unknown 后盲重发或代替 Core 裁决 |

角色是任务中的职责，可由不同受管 Agent 或可信确定性程序承担；同一 Provider 的不同执行也可独立协作，不强迫多品牌。Leader 必须是贯穿全程、可反复唤起的受管语义调用，不能只把现有 Planner 等标签组合起来即称完成，也不需要常驻进程或新的用户可管理业务实体。Leader 若参与某份成果实现，该部分仍须由其他执行进行必需审查/验收。客观验收不必多调用 LLM；语义 Reviewer 意见不是唯一成功证据。

四责明确为：Supervisor 只观察、聚合异常/证据并通知，不业务换人/重试/改计划/判成败，不因疑似 stuck 直接 kill；Leader 做业务判断；Core 保存事实并校验授权/预算/依赖/当前证据，执行已批准调度和硬规则；Execution 实际操作所属 handle。用户 cancel、硬期限/预算规则、owner 失去的停止新派发及已退出事实处理不等 LLM；依赖就绪的已批准工作由 Core 直接派发，停止后是否换方案才交 Leader。当前 `TaskSupervisor` 混合了这些职责，目标在原 loop 中委托接口，不以文档宣称已拆分。

完整行为、最小行动集、真实代码接缝和统一实施顺序见 [Leader 执行机制](../node-leader-execution-design.md)，状态为 `DESIGN`。同 Task 至多一个 Leader 在途，业务事件聚合；token/progress/heartbeat 不逐条唤起。读取语义快照/manifest 与 cursor，按相关候选/授权/答案/决定当前性接纳，不因无关进度制造失效重规划风暴。决定与动作/outbox 同库提交；已提交先恢复原动作，未提交仅在原义务、清理及剩余预算内有限重试，不抹费用。外部 unknown 必须 reconcile，不宣称跨系统 exactly-once。

Core 必须在原 Task/全局硬容量中保留业务决策 headroom 或减少作者并发；Leader 仍计资源/预算。两个作者并行的代表 profile 付费前须证明有 Leader 容量，不静默提额、不假释放待答席位。否则两个占满容量的待答作者会使 Leader 永久排队；此为整链必测活性反例，不是新调度平台。

## 3. 业务发布授权与恢复底线

本稿接受有界业务发布设计，不为任何当前 Task 自动授予目标写权限。实际启用前，同一纵切必须冻结并实现：用户授权来源及有效范围、Task/计划与精确成果/Decision 摘要、动作和目标、有效期限/撤销、幂等身份、原请求及结果观察。引用可复用原批准/Operation/Store 语义，不另建授权平台；新增机器字段/持久事实须在实现时明确版本及旧 reader 拒绝，不能静默改变旧记录含义。

- 默认不发布；明确授权可覆盖一段边界清楚的低风险交付，不要求每条普通工具操作再问一次。破坏性/不可逆操作、生产数据变更、权限/凭据变更、对外通知及费用超限等高风险动作，缺少针对该动作和目标的明确批准就暂停请求授权；普通业务答案不替代它。
- 发布前由 Core 重验当前计划、必需独立验收/Review、成果摘要、授权和 cancel/期限；作者或 Leader 的新文本不能扩权。业务材料和外部返回仍视为数据，不作为授权指令。
- 先耐久发布意图与幂等绑定，再锁外执行，最后按当前 owner/原请求接纳真实回执。丢响应/服务重开先查原回执或外部目标；没有可查询/幂等依据则保持 unknown，不能用新 key、新 Task 或改状态重发。发布后检查不延长原预算/期限。
- 取消可阻止未开始的发布；已发生的外部效果不能因取消、数据库回滚或停止 Agent 而被宣称撤销。回滚/补偿是另一个需要明确授权的动作，原失败、效果与检查证据保留。
- 新完整 Leader profile 的候选验收通过只是阶段完成，须延迟整体 terminalization 至 Leader 汇总被接纳、用户要求的授权交付/后验全部满足且无待决成功义务。发布成功、检查成功及总体结果分别记录；检查失败/未知不得改写先前回执为未发布。当前 verifier 成功直接 `completed` 的语义不能悄改，须随新 profile/格式与严格客户端兼容一起实现；旧 `completed` 不复活，原回执/历史不重解释。
- 秘密不进入提示、业务事件、普通日志或下载；输入审计继续默认 metadata-only，显式受信披露策略及旧格式限制保持。不得为本 profile 复制 HOME、搜集凭据或关闭 OS/企业安全机制。

## 4. 两种发布必须分开

**产品业务发布**是 Marshal 帮用户交付任务成果，例如把已验收版本发布到明确的测试目标；它必须经过上节的业务授权、精确证据和幂等/恢复链。首个代表性目标选择可检查、可限定且低风险的目标，不把全部云平台、生产 SQL、支付、不可逆迁移等未来流程作为首发前置。

**Marshal 软件发行**是维护者分发 Marshal 自身的版本/安装包。现有只读 candidate admission、CI 与同资产安装消费不是发行授权；受保护 same-bytes stable、声明平台实机、故障/长期运行/备份恢复及支持矩阵仍属于 B3。原生资产签名/公证按 ADR0088 §6 适用；纯 JS 包不伪称 notarized。Leader 业务发布能力不获得仓库 tag/release、CI 权限变更、软件签名或保护分支权限，研发维护者权限也不转授产品 Agent。

## 5. 当前代表性闭环与实施顺序

正式发布前单列 `B2-L` 完整闭环：明确业务目标/上下文→Leader必要澄清与有限角色计划→精确确认→两个互补Worker→独立Reviewer→需要时局部修正并保留无关成果→独立整体验收→明确授权的有限目标交付→独立后验→Leader汇总原回执与证据、Core接纳整体结果。正常任务不要求必须返工；局部修正另须真实Agent及实际独立拒收/修正/重新验收链证明，允许选择运行前已存在可复现业务缺陷的有限案例，但普通修bug不替代repair接缝实证。自然任务、明确标注的缺陷修复实机、确定性故障分别报告，不无限付费等模型犯错。原Worker取消、问答、单写者、原期限/预算、旧owner/迟到拒绝和cleanup-only恢复不削减；不得人为污染候选/伪造拒收来凑证据。

先复用当前Node Application/SQLite、Provider、受管执行、File/Git Business、独立Verification和HTTP/客户端，不恢复Workspace/Project注册、Marshal skill、统一Agent Skill/登录、动态插件平台或通用Workflow引擎。一次对齐最小行动/持久语义/兼容，然后按需求/首次执行、结果驱动协调/局部调整、授权交付/后验、最终支持面形成同链可运行检查点；每步同步对应故障/兼容和有界真实验证，不等全部实现后才首次集成。不是多个微功能或重做已通过子链；B3准备并行，最终发行仍验完整同一资产。

同一完整实现验证 [六类组合出口](../node-leader-execution-design.md)：正向全链、聚合/当前性/原预算、权限与独立性、取消/硬规则/失败、决定与外部效果各 COMMIT 窗口恢复、旧协议及后继任务。B1 的既有七条件由独立实证另行裁定，不因本设计自动通过；其本机 PoC 通过也不代替 `B2-L` 或 stable。

真实成功流程重复、范围稳定后，再将角色/输入/验收/授权边界固化为可复用 Workflow Template。模板只是经过验证的任务配置，实例仍需具体目标、输入与授权；不携带通用凭据或无限权限，不复用旧 Decision。首发不要求模板市场、编辑器、任意动态高风险流程或团队普遍胜过单 Agent 的证明。

## 6. 实现与证据状态

本提交仅调整设计和导航，未修改运行时、API、Schema、Store 格式、现存数据、发布工具或实机驱动。已有普通用户实机仍是原记录中的 dogfood/non-production，API-STABLE 仍仅是已核验接口检查点；受管 Leader 全生命周期/发布/后验为 `DESIGN`，没有新增强隔离、Linux 模型部署或 stable 实证。B1 可信单用户本机 PoC 的单独通过依据见当前 Roadmap，不能外推本机制；B2/B3 继续按真实出口推进。

## 7. 2026-09-09 业务正确性与效率细化

本节依据用户对业务交付审计的修改要求，细化本ADR已有目标、独立验收和有界自治；不新增运行权限、持久格式、动态代码执行或旧记录解释。具体行为和验收统一见[Leader机制](../node-leader-execution-design.md)，实际机器接缝仍须按原合同一次明确兼容后启用。

- 在现有Task/Plan内容中分清原始需求、确认后的交付约定与实现计划；必需要求对应实际工作包、成果与独立证据。Leader负责业务意义，独立Reviewer检查需求/验收覆盖；Core验证已确认记录和证据，不能证明任意自然语言理解正确。测试全绿但遗漏必需要求不成立整体成功。
- 可信验证机制与任务验收内容分开；在支持的业务能力内提议、检查和冻结内容，不因模型提出新断言就允许任意Shell/SQL或扩权。作者不能事后降低标准；同业务族两个不同需求用同一服务及业务/验证能力配置、只经Task公开输入变化完成，不临时改Core或手工验收。
- 原批准自治范围内的实现细节、已支持替换/局部修正不逐次打断用户；目标/成果/标准/预算或外部写权限实质变化先精确确认，未支持拓扑不因批准就可运行。建议性润色不自动变成新的必需交付。
- 正常任务可以首通，修正与故障能力仍单独取真实且可追溯的证据；持续接线而非末尾一次大集成。原API-STABLE保留原范围，包含Leader决定/授权/阶段与整体结束的新支持面须在正式候选重新核验。
