# ADR 0094：可信单用户角色团队与有界授权交付

- 状态：Accepted（2026-09-09；依据用户本轮明确要求以可信单用户环境中的 Leader、开发、Reviewer、验收等角色团队收敛当前交付，强 OS 账号/凭据隔离证明后置。此为设计范围接受，不是实现审查通过或运行许可回执）。
- 适用：ADR0088 的 Node Task 服务，目标支持 profile 名称为 `trusted-single-user`；本稿不新增已可用配置项、API、持久格式或自动发布能力。
- 基线：`31afe269f25241c4ff9fde19c03478cbfddb85a7`。实际成熟度见 [Roadmap](../roadmap-status.md#业务交付当前表)，实施出口见 [Milestone](../agent-team-service-milestones.md)。

## 1. 决策与精确取代范围

当前先交付能完成真实业务的受信角色团队，不以证明同 UID 下完全隔离宿主凭据作为前置。信任单个操作者、其选定的 Agent/模型、受信组合代码与允许执行的业务材料；不支持恶意 Worker、敌对依赖、多租户或凭据窃取对抗。共享 OS 用户意味着这些进程可能触达该用户的文件、原生登录与外部工具，角色名、环境过滤、工具回调和本地 token 均不能证明强隔离。

| 原约束 | 本 profile 的调整 | 不变部分 |
| --- | --- | --- |
| ADR0085 §3、ADR0088 §3：作者可达 Publisher 凭据/已登录发布入口即不进入支持范围，`publication:none` 也不例外 | 对 `trusted-single-user`，不再要求先证明 OS 账号/凭据不可达；明确保留 ambient credential 风险，强隔离作为后继加固支持项 | 作者没有产品发布授权，不主动发现/输出秘密；默认 `publication:none`，原生登录不代表批准任何外部写 |
| Worker/Publisher 分权 | 当前要求产品职责、命令准入与证据权威分离；不宣称已用 OS 身份强制隔离 | 开发者不能自签验收或自行接纳发布，Core 仍独占权威事实；旧 Go/hardened profile 的强边界不变 |
| 首版只下载成果，外部发布全部后置 | 保留下载默认；增加一个明确授权、目标有限、可观察回执的代表性业务发布及发布后验证闭环作为后继完整实现 | 未实施/未实测能力不能从提示词直接启用；无授权、超范围、高风险缺批准或效果未知时拒绝继续写 |
| 固定规划/作者/验证角色 | Leader 组织理解、分工、评审与交付；按任务选有限角色，不要求所有任务固定人数 | Supervisor 仍是确定性 Core；不新增角色 CRUD、任意动态工作流或第二状态机 |

本 ADR 只改变所列 Node 目标支持面的信任假设和排期。ADR0051/0052/0068、旧 Go 执行/Publisher、hardened conformance、远程认证与全部旧运行记录保持原合同。不得给旧证据改 `production=true`、重签或从本稿推导旧部署已获强隔离证明；后继受支持声明须明确本 profile 和剩余风险，而非隐去限制。

**兼容性**：本次是目标/profile 合同与排期调整，不修改现有 HTTP 请求/响应、角色枚举或持久格式，无数据迁移，不撤回 API-STABLE 已验证范围。它不是当前软件的协议 breaking change，但也不承诺未来发布实现“一切向后兼容”：若新增角色枚举、终态或副作用记录会影响严格客户端/旧 reader，须随完整实现明确 API 版本或兼容方式、格式选择及旧根拒绝/升级策略，不把未识别值静默解释成旧成功。

## 2. 角色团队，不是监督 Agent 取代 Core

| 职责 | 可以做什么 | 不能做什么 |
| --- | --- | --- |
| Leader | 理解目标、提出必要问题和有限分工、协调开发/Reviewer/验收、汇总证据；在既定授权内请求发布并组织发布后验证 | 直接改状态/预算/授权，凭自己的总结签通过，绕过必需 Reviewer 或把发布请求当成功 |
| 开发 Worker | 在批准输入与节点范围内产出候选、报告实际问题，必要时请求业务答案 | 自改验收标准、给自己的成果签权威 Decision、借原生登录自行发布 |
| Reviewer | 独立读取精确候选与证据，提出有界语义意见/集中修正建议 | 为自己参与编写的同一成果承担唯一独立评审，凭角色标签替代真实检查 |
| 验收执行 | 在作者之外验证冻结的整体业务断言与制品；发布后按授权检查实际目标 | 接受作者的 pass 文本、改低原断言、把本地文件存在当外部业务效果 |
| 发布执行职责 | 仅消费已授权且经当前证据接纳的精确成果，执行有限外部动作并返回真实回执 | 自授发布权限、改变目标/成果、在 unknown 后盲重发或代替 Core 裁决 |

角色是任务中的职责，可由不同受管 Agent 或可信确定性程序承担；同一 Provider 的不同执行也可独立协作，不强迫多品牌。Leader 先作为现有规划/协调/评审职责的组合，不急于新增 Core 业务实体或公开角色枚举。Leader 若参与某份成果实现，该部分仍须由其他执行进行必需审查/验收。客观验收不必多调用 LLM；语义 Reviewer 意见不是唯一成功证据。

Core 继续接纳计划、校验权限与证据、预留预算、调度、记录取消/结果及发布事实。角色建议只进入已有应用命令/业务接缝，不获得 Store 写权。运行时角色选择、发布执行接缝和记录尚未实现者保持待实现；不以改显示名把当前 planner/author/verifier 冒充完整 Leader。

## 3. 业务发布授权与恢复底线

本稿接受有界业务发布设计，不为任何当前 Task 自动授予目标写权限。实际启用前，同一纵切必须冻结并实现：用户授权来源及有效范围、Task/计划与精确成果/Decision 摘要、动作和目标、有效期限/撤销、幂等身份、原请求及结果观察。引用可复用原批准/Operation/Store 语义，不另建授权平台；新增机器字段/持久事实须在实现时明确版本及旧 reader 拒绝，不能静默改变旧记录含义。

- 默认不发布；明确授权可覆盖一段边界清楚的低风险交付，不要求每条普通工具操作再问一次。破坏性/不可逆操作、生产数据变更、权限/凭据变更、对外通知及费用超限等高风险动作，缺少针对该动作和目标的明确批准就暂停请求授权；普通业务答案不替代它。
- 发布前由 Core 重验当前计划、必需独立验收/Review、成果摘要、授权和 cancel/期限；作者或 Leader 的新文本不能扩权。业务材料和外部返回仍视为数据，不作为授权指令。
- 先耐久发布意图与幂等绑定，再锁外执行，最后按当前 owner/原请求接纳真实回执。丢响应/服务重开先查原回执或外部目标；没有可查询/幂等依据则保持 unknown，不能用新 key、新 Task 或改状态重发。发布后检查不延长原预算/期限。
- 取消可阻止未开始的发布；已发生的外部效果不能因取消、数据库回滚或停止 Agent 而被宣称撤销。回滚/补偿是另一个需要明确授权的动作，原失败、效果与检查证据保留。
- 若用户要求发布及发布后检查，仅下载成功不代表该业务目标完成。发布成功、检查成功及总体结果分别记录；检查失败/未知不得改写先前回执为未发布。已有 `completed` Task 不被此设计复活；必要后继显式关联原成果和授权，不重置已有任务成本。
- 秘密不进入提示、业务事件、普通日志或下载；输入审计继续默认 metadata-only，显式受信披露策略及旧格式限制保持。不得为本 profile 复制 HOME、搜集凭据或关闭 OS/企业安全机制。

## 4. 两种发布必须分开

**产品业务发布**是 Marshal 帮用户交付任务成果，例如把已验收版本发布到明确的测试目标；它必须经过上节的业务授权、精确证据和幂等/恢复链。首个代表性目标选择可检查、可限定且低风险的目标，不把全部云平台、生产 SQL、支付、不可逆迁移等未来流程作为首发前置。

**Marshal 软件发行**是维护者分发 Marshal 自身的版本/安装包。现有只读 candidate admission、CI 与同资产安装消费不是发行授权；受保护 same-bytes stable、声明平台实机、故障/长期运行/备份恢复及支持矩阵仍属于 B3。原生资产签名/公证按 ADR0088 §6 适用；纯 JS 包不伪称 notarized。Leader 业务发布能力不获得仓库 tag/release、CI 权限变更、软件签名或保护分支权限，研发维护者权限也不转授产品 Agent。

## 5. 当前代表性闭环与实施顺序

唯一新增完整闭环为：明确业务目标/上下文→Leader 必要澄清与有限角色计划→精确确认→互补开发并行→独立 Reviewer（计划需要时）与整体验收→精确成果/下载→明确授权的单一测试目标发布→发布后独立检查→汇总原回执、失败与审计。原 Worker 取消、问答、同计划局部修正、单写者、原期限/预算、旧 owner/迟到结果拒绝和 cleanup-only 恢复均不削减。

先复用当前 Node Application/SQLite、Provider、受管执行、File/Git Business、独立 Verification 和 HTTP/客户端，不恢复 Workspace/Project 注册、Marshal skill、统一 Agent Skill/登录、动态插件平台或通用 Workflow 引擎。B1/B2 已有工作和证据保留；B2 按新用户闭环补最薄的授权业务交付，B3 仍验收可靠性与软件资产发行。当前已有 planner→作者→独立 checker→下载/正常重开及限定故障证据继续计入，不重跑来制造新成绩；尚缺的 Leader 角色协调、业务发布/发布后验证必须真实接线后单独验收。

同一完整实现至少验证：作者自证/陈旧成果被拒；无授权及超目标零发布；原回执丢响应/冷开不重复外部写；cancel/期限与发布竞争；发布已发生但检查失败仍保留真实非全成功结论；合法闭环与后续新任务可用。全部通过前，不因强隔离后置整体关闭 B1 或宣布 stable。

真实成功流程重复、范围稳定后，再将角色/输入/验收/授权边界固化为可复用 Workflow Template。模板只是经过验证的任务配置，实例仍需具体目标、输入与授权；不携带通用凭据或无限权限，不复用旧 Decision。首发不要求模板市场、编辑器、任意动态高风险流程或团队普遍胜过单 Agent 的证明。

## 6. 实现与证据状态

本提交仅调整设计和导航，未修改运行时、API、Schema、Store 格式、现存数据、发布工具或实机驱动。已有普通用户实机仍是原记录中的 dogfood/non-production，API-STABLE 仍仅是已核验接口检查点；没有新增 Leader 发布、动态角色、强隔离、Linux 模型部署或 stable 实证。OS/凭据强隔离从当前 profile 的阻断项转为后继加固，剩余业务/恢复/发行出口仍按真实证据逐项关闭。
