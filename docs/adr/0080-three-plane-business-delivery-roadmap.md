# ADR 0080：三面分离与业务交付驱动的 Agent Team 路线

- 状态：已接受（Accepted，2026-09-05，维护者明确要求按本轮审计建议更新设计并实施）。接受的是产品范围与实施顺序，不是实现、独立验证或发布证据。
- 关联：ADR 0019、0052、0062、0079；Issue #186、#195、#205、#212；[业务交付计划](../agent-team-delivery-plan.md)。

## 背景

fixed CLI 已有真实 Pi 到 `ACCEPTED` 的证据，fixed server T1 已证明 restart/response-loss；PR #254 已合入 T2 生命周期接口。但这不等于从用户需求到多 Agent 集成交付的持续闭环。仓库级长锁、整体恢复故障域、历史账本全量重放，以及反复在实现后才暴露的环境/契约问题，使增加 Worker 数量不必然增加吞吐。

## 决策

### 1. 精确调整发布范围，不复活整个 M13

部分取代 ADR 0052 §2/§6 将全部 Goal 编排推迟到 1.x 的排期：正式产品目标增加一个受限 Agent Team profile，按 `B1 → B2 → B3` 验收。B1 是既有 fixed server 单任务闭环；B2 是单仓库、单用户、最多三个并发实现节点、明确集成候选的团队闭环；B3 是该支持面的恢复、长期运行及正式分发。复杂通用 DAG、多租户、HA、全部 Provider、自动 merge 仍不纳入。

I186-R0→R6 保留为技术证据映射，历史成熟度不因本 ADR 升级；B1/B2/B3 是用户能力退出条件，不是三套新 Runtime。可以先发布明确标识的运行内核预览，但 B2 未通过不能声称自治 Agent Team 产品完成。ADR 0052 的签名、公证、Linux、故障与发布门禁不删除。

### 2. 三面边界

- 控制面：唯一接纳 Task/Goal proposal、管理计划/预算/依赖、授权执行、接纳结果及发布决策。CLI/UI/Skill 是客户端，不保存第二份权威状态。
- 执行面：有界 Agent/Verifier 工作负载与环境管理，只返回观察/候选。Verifier 身份、工作区和证据权限与作者分离；Publisher 仍属于独立 publication 信任域，不因三面部署图而并入 Worker。
- 存储面：权威账本与内容寻址制品的持久设施；Core 独占权威写入，执行者只能经授权接纳通道提交。索引、队列、缓存与统计可重建。

首个部署为一个 fixed `marshal control-plane serve`、多个执行进程和现有 file-backed ledger/object store。逻辑分离不要求新增 RPC/存储服务，不把单机信任描述成多租户或 hostile-code 隔离。以后替换数据库/对象存储或启用远程执行，须保持现有授权边界并另立具体迁移 ADR。

### 3. 受限团队流程

用户意图 → 关键假设澄清 → 明确验收与方案确认 → Core 接纳版本化计划 → 有界任务 → 集成候选 → 独立验证/评审 → 授权交付。

复用 ADR 0019 的 proposal/admission、approval、累计预算、reservation/outbox 同事务、依赖失效和 Goal `PAUSED` 语义；不以小 profile 为由绕过它们。最多三个是首个 profile 的实现并发上限，不是全局节点/预算合同；Verify/Review/集成也占用各自资源。修改冻结 Run 输入必须新建关联 Run，终态不复活。新持久字段、materialization 与集成身份的具体原子边界必须在 B2 实现前另立窄 ADR，不允许靠本路线文档发明平行 JSON 状态机。

完成条件绑定集成候选和用户验收；所有子 Run 通过不等于 Goal 完成。变更候选、接口或计划时只重验受影响依赖，不抹掉已完成的无关成果。

### 4. 效率与恢复

先验证最可能使整轮作废的假设，再实现完整功能。任务按用户可验收能力拆分，不按 Schema/文件拆分。区分 transient retry、局部 rework、契约 replan 和环境阻塞；相同结构性失败复发时冻结同类重试，保留证据并修正假设，不停止无关任务。

机器监督负责资源/超时/重复失败，语义监督只提交偏离目标与重规划建议。等待用户和 Provider 不长期占据实现 Worker。恢复单位为已确认计划、任务事实和制品，不保证复活原 Agent 会话。

仓库级长锁收敛为短提交与任务级执行保护、单 Run 隔离及账本检查点均是待实现改进，不在本 ADR 中静默改变既有 recovery-before-ready、lease 或 evidence 合同；各自需要真实故障证明及必要的窄 ADR。

## 验收与代价

以固定参考业务场景和 Marshal 自身开发两类 dogfood 交错验证；使用固定执行版本、独立 oracle 和候选摘要，修改中的系统不能自签通过。先得到单 Agent 时间/质量基线，再比较团队结果；不要求非确定性 patch 字节相等。记录失败的分母、人工介入、等待、重做时间及缺失 token 数据，不以 PR 数量替代交付。

代价是正式 Agent Team 产品比单任务内核多一条明确 B2 门禁；通过限制首个 profile 而不是开放通用框架控制成本。既有未关闭的 signing、launcher、Linux 和恢复故障不能被参考测试通过掩盖。
